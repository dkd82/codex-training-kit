      Jour 1 — Présentation des travaux pratiques

      Thème du jour : prise en main de Codex et génération assistée. Ce guide couvre les TP 1 à 3. Les TP 4 à 7 font l'objet d'un guide séparé (Jour 2).

      Le fil rouge : un mini-outil de facturation

      Pendant les deux jours, vous faites vivre un même projet : un outil de facturation en ligne de commande, en Python. Aujourd'hui vous le créez (TP 1), vous apprenez à l'interroger par l'API (TP 2), puis vous y ajoutez un module de remises avec ses tests et sa documentation (TP 3). Demain, vous l'étendrez avec des actions, des tools, des agents et un refactor. C'est le « projet fil rouge » du programme.

      ★
      Votre état d'esprit pour tous les TP

      Codex accélère, vous gardez la maîtrise : vous demandez un plan avant de coder, vous relisez le diff, vous lancez les tests, et vous itérez. Un TP réussi, ce n'est pas « Codex a tout fait » : c'est « le résultat est correct, testé et compris ».

      Ces durées sont indicatives ; chaque TP contient des parties « cœur » (à faire) et « bonus » (si vous avez de l'avance). Ils correspondent aux « mises en pratique du Jour 1 » du programme.

      Les 4 réflexes à appliquer à chaque TP

      1. Cadrer : un prompt structuré (objectif, contraintes, style, format attendu).
      2. Planifier avant de coder : demander un plan en lecture seule, le relire, le corriger.
      3. Contrôler : relire le diff (git diff), lancer les tests, ne jamais accepter à l'aveugle.
      4. Protéger : permissions minimales, aucun secret dans le code ni dans les prompts partagés.

      À partir du TP 3, tout le monde repart du même code (base_facturation), quel que soit le résultat obtenu au TP 1.

      TP 1 — Initialiser un projet et générer sa structure

      RubriqueDétail
      Jour / duréeJour 1 — 60 minutes (indicatif)
      StarterStarters/tp1_initialiser
      Compétencesplan avant code, permissions, génération multi-fichiers, contexte persistant (AGENTS.md)
      Livrableun projet Python qui passe ses tests, un AGENTS.md, au moins un commit

      Objectifs

      • Faire générer par Codex la structure complète d'un projet à partir d'un cahier des charges.
      • Appliquer le réflexe « plan d'abord » : lecture seule, relecture, validation, puis génération.
      • Créer le contexte persistant du projet (AGENTS.md) et constater son effet.

      Mise en route

      Ouvrez le dossier tp1_initialiser dans votre IDE. Il contient uniquement specs/cahier_des_charges.md : lisez-le en entier (5 min).

      Terminal (macOS / Linux / Git Bash)bash
      cd tp1_initialiser
git init
python -m venv .venv
source .venv/bin/activate
python -m pip install pytest
      Terminal (Windows PowerShell)powershell
      cd tp1_initialiser
git init

python -m pip install pytest
      i

      Lancez Set-ExecutionPolicy -Scope Process Bypass puis réessayez, ou utilisez directement .venv\Scripts\python.exe -m pytest.

      Étape 1 — Demander un plan (lecture seule)

      Lancez Codex dans le dossier (codex, ou le panneau Codex de votre IDE). Avant d'écrire du code, réglez les permissions en lecture seule et demandez un plan d'implémentation. Vous ne devez voir apparaître aucun fichier créé.

      Squelette de prompt (à compléter)à remplir
      Champ libre : écrivez votre propre prompt par-dessus le squelette. Enregistré automatiquement sur cet appareil.

      Étape 2 — Relire et corriger le plan

      Relisez le plan avec cette grille : les 6 fichiers de facturation/ sont-ils prévus ? Les tests sont-ils prévus ? Decimal partout ? Aucune dépendance externe ? Chaque étape est-elle vérifiable ? Corrigez ou complétez par un message de suivi, jusqu'à ce que vous validiez le plan.

      Étape 3 — Générer le projet (permissions « Auto »)

      Passez les permissions en Auto (lecture, édition et exécution de commandes dans le dossier de travail), puis demandez à Codex d'appliquer le plan validé. Codex doit aussi lancer les tests et corriger jusqu'au vert.

      Squelette de prompt (à compléter)à remplir
      Champ libre : écrivez votre propre prompt par-dessus le squelette. Enregistré automatiquement sur cet appareil.

      Étape 4 — Contrôler le résultat

      1. Lancez vous-même python -m pytest -q (ne vous fiez pas au seul message de Codex).
      2. Lancez python -m facturation --help : les 4 commandes sont-elles présentes ?
      3. Jouez le scénario complet (voir « Critères de réussite »).
      4. Relisez le diff : git status puis git diff (ou /diff si votre version l'a). Y a-t-il des fichiers inattendus ? Des float ?
      5. Faites un premier commit.
      Scénario de contrôlebash
      python -m facturation --data donnees ajouter-client --id C1 --nom ACME --email contact@acme.example
python -m facturation --data donnees creer-facture --numero F-001 --client C1 --emission 2025-01-10 --echeance 2025-02-09 --ligne "Stylo;10;1.50"
python -m facturation --data donnees lister
python -m facturation --data donnees afficher F-001
git add -A
git commit -m "TP1 : projet facturation généré avec Codex"

      Étape 5 — Créer le contexte persistant (/init puis AGENTS.md)

      Dans Codex, lancez /init : Codex génère un premier AGENTS.md. Relisez-le, puis complétez-le avec les conventions de votre projet (commandes d'installation, de test et de lancement ; Decimal ; tests obligatoires ; aucun secret ; ne jamais toucher à donnees/).

      Squelette de prompt (à compléter)à remplir
      Champ libre : écrivez votre propre prompt par-dessus le squelette. Enregistré automatiquement sur cet appareil.

      Étape 6 — Vérifier l'effet de AGENTS.md

      Ouvrez une nouvelle session Codex dans le même dossier et demandez une petite évolution. Vérifiez que Codex respecte les conventions sans que vous les répétiez (types, Decimal, test ajouté).

      Squelette de prompt (à compléter)à remplir
      Champ libre : écrivez votre propre prompt par-dessus le squelette. Enregistré automatiquement sur cet appareil.

      Livrables et critères de réussite

      Pièges à éviter

      • Tout demander en un seul prompt géant : découpez (plan → génération → contexte).
      • Accepter le résultat sans lancer les tests vous-même.
      • Laisser passer un float ou une dépendance non demandée.
      • Oublier que le prompt vague donne un résultat vague : reprenez la structure objectif / contraintes / style / format.

      Pour aller plus loin

      • Demandez à Codex d'expliquer un module de son choix (/review sur une petite partie du code).
      • Ajoutez un test de régression pour un cas limite (facture sans ligne, quantité nulle).

      TP 2 — Appeler un prompt en ligne de commande avec l'API

      RubriqueDétail
      Jour / duréeJour 1 — 40 minutes (indicatif)
      StarterStarters/tp2_api
      CompétencesAPI OpenAI (API Responses), variables d'environnement, itération d'un prompt, comparaison avec codex exec
      Livrableun script qui envoie prompt.txt au modèle et affiche la réponse ; deux versions du prompt comparées

      Objectifs

      • Comprendre ce qui se passe « sous le capot » : une requête HTTP avec un prompt, une réponse en texte.
      • Manipuler une clé d'API sans jamais l'écrire dans un fichier.
      • Constater l'effet de la qualité du prompt sur le résultat, puis comparer avec l'agent Codex en mode non interactif.
      !
      Avant de commencer : la clé d'API

      Votre clé vous est fournie. Placez-la uniquement dans une variable d'environnement de votre terminal. Ne la collez ni dans un fichier, ni dans un prompt, ni dans un chat.

      Étape 1 — Préparer l'environnement

      macOS / Linux / Git Bashbash
      cd tp2_api
python -m venv .venv && source .venv/bin/activate
python -m pip install -r requirements.txt
export OPENAI_API_KEY="collez_votre_cle_ici"
export OPENAI_MODEL="nom_du_modele_indique_par_le_formateur"
      Windows PowerShellpowershell
      cd tp2_api
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
$env:OPENAI_API_KEY = "collez_votre_cle_ici"
$env:OPENAI_MODEL = "nom_du_modele_indique_par_le_formateur"

      Ces variables ne vivent que dans la fenêtre de terminal courante : c'est voulu.

      Étape 2 — Écrire le prompt

      Ouvrez prompt.txt et remplacez chaque TODO. Sujet imposé : demander la fonction Python jours_de_retard(echeance, aujourdhui) qui retourne le nombre de jours de retard d'une facture, accompagnée de tests pytest.

      Squelette de prompt (à compléter dans prompt.txt)à remplir
      Champ libre : écrivez votre propre prompt par-dessus le squelette. Enregistré automatiquement sur cet appareil.

      Étape 3 — Compléter le script d'appel

      Choisissez un des trois scripts (Bash, PowerShell ou Python) et complétez les TODO. La requête est un POST sur https://api.openai.com/v1/responses avec un corps JSON contenant model et input, et un en-tête Authorization: Bearer <clé>.

      Lancer le script choisibash
      bash appel_api.sh          # Bash + curl + jq
      Ou sous PowerShellpowershell
      .\appel_api.ps1
      Ou en Pythonbash
      python appel_api.py

      Étape 4 — Lire et itérer

      1. Lisez la réponse : la fonction respecte-t-elle vos contraintes ? Les tests sont-ils pertinents ?
      2. Modifiez une chose dans prompt.txt (une contrainte, le format) et relancez.
      3. Notez les différences entre les deux réponses : quelle modification a eu le plus d'effet ?

      Étape 5 — Comparer avec Codex en mode non interactif

      codex exec lance Codex sans interface : il travaille sur le dossier courant et écrit sa réponse sur la sortie standard. Utilisez le mode lecture seule.

      Même demande, via Codexbash
      codex exec --sandbox read-only "$(cat prompt.txt)"
      Sous PowerShellpowershell
      codex exec --sandbox read-only (Get-Content prompt.txt -Raw)

      Comparez : qu'est-ce qui diffère entre l'appel API brut et l'agent Codex (contexte du dossier, outils, durée) ? Quand choisir l'un ou l'autre ?

      Livrables et critères de réussite

      Pièges à éviter

      • Coller la clé dans le script « pour tester » : c'est ainsi que les clés fuient.
      • Sous PowerShell, curl est un alias de Invoke-WebRequest : utilisez Invoke-RestMethod ou curl.exe.
      • Construire le JSON à la main : guillemets et retours à la ligne cassent la requête (utilisez jq, ConvertTo-Json ou le SDK).
      • Erreur « modèle introuvable » : votre compte n'a pas accès à ce modèle, changez la variable OPENAI_MODEL.

      Pour aller plus loin

      • Affichez la consommation de la requête (le champ usage de la réponse) pour estimer le coût en tokens.
      • Écrivez la réponse dans un fichier .py et lancez les tests générés.

      TP 3 — Générer un module, ses tests et sa documentation

      RubriqueDétail
      Jour / duréeJour 1 — 70 minutes (indicatif)
      StarterStarters/base_facturation (+ specs/remises.md)
      Compétencesplan, tests d'abord, génération d'un module, documentation cohérente, revue
      Livrablefacturation/remises.py, tests/test_remises.py, docs/remises.md — alignés entre eux

      Objectifs

      • Générer un module et ses tests et sa documentation, en garantissant leur cohérence (mêmes règles, mêmes chiffres).
      • Pratiquer le « tests d'abord » avec un assistant IA.
      • Contrôler la qualité : lecture du diff, revue de code assistée, vérification de l'exemple chiffré.

      Mise en route

      À partir de ce TP, tout le monde repart de base_facturation (copiez le dossier, quel que soit votre résultat au TP 1).

      macOS / Linux / Git Bashbash
      cp -r base_facturation tp3_remises && cd tp3_remises
git init && git add -A && git commit -m "Base"
python -m venv .venv && source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python -m pytest -q          # attendu : 9 tests au vert
      Windows PowerShellpowershell
      Copy-Item -Recurse base_facturation tp3_remises; cd tp3_remises
git init; git add -A; git commit -m "Base"
python -m venv .venv; .venv\Scripts\Activate.ps1
python -m pip install -r requirements-dev.txt
python -m pytest -q          # attendu : 9 tests au vert

      Lisez specs/remises.md en entier : les règles, l'API attendue et l'exemple de référence (brut 1 000,00 € → net 850,00 €) sont votre source de vérité.

      Étape 1 — Planifier (lecture seule)

      Demandez à Codex un plan en lecture seule : fichiers à créer, fonctions, cas de tests, et la façon dont il garantira la cohérence code / tests / documentation.

      Squelette de prompt (à compléter)à remplir
      Champ libre : écrivez votre propre prompt par-dessus le squelette. Enregistré automatiquement sur cet appareil.

      Étape 2 — Écrire les tests d'abord

      Validez le plan, passez en permissions Auto, puis demandez uniquement les tests de tests/test_remises.py. Lancez-les : ils doivent échouer (le module n'existe pas encore) et échouer pour la bonne raison.

      Squelette de prompt (à compléter)à remplir
      Champ libre : écrivez votre propre prompt par-dessus le squelette. Enregistré automatiquement sur cet appareil.

      Étape 3 — Générer le module

      Demandez maintenant facturation/remises.py, avec pour consigne de faire passer tous les tests sans modifier les tests ni les autres modules.

      Squelette de prompt (à compléter)à remplir
      Champ libre : écrivez votre propre prompt par-dessus le squelette. Enregistré automatiquement sur cet appareil.

      Étape 4 — Générer la documentation, puis vérifier la cohérence

      Demandez docs/remises.md : objectif, règles, exemple chiffré, utilisation. Puis vérifiez vous-même : l'exemple chiffré de la documentation est-il identique à celui d'un test ? Les règles décrites correspondent-elles au code ?

      Squelette de prompt (à compléter)à remplir
      Champ libre : écrivez votre propre prompt par-dessus le squelette. Enregistré automatiquement sur cet appareil.

      Étape 5 — Revue de code assistée et contrôle du diff

      1. git status : seuls 3 fichiers nouveaux doivent apparaître. Aucun module existant modifié.
      2. git diff (ou /diff) puis lisez remises.py ligne à ligne.
      3. Lancez une revue par Codex : /review, ou dans le terminal codex review --uncommitted.
      4. Traitez les remarques pertinentes (relancez les tests après chaque changement), puis committez.

      Livrables et critères de réussite

      Pièges à éviter

      • Laisser Codex écrire code et tests d'un coup : les tests deviennent un miroir du code et ne prouvent plus rien.
      • Accepter une documentation « plausible » dont les chiffres ne correspondent pas aux tests.
      • Ne pas vérifier les frontières (9 contre 10, 49 contre 50) : c'est là que les bugs se cachent.
      • Modifier calculs.py « pour faciliter » : la consigne est de réutiliser, pas de modifier.

      Pour aller plus loin

      • Intégrez les remises dans la commande afficher (option --code-promo) avec ses tests.
      • Demandez à Codex de trouver des cas limites que vous n'avez pas testés (Find Bugs), puis vérifiez ses propositions.

      Niveaux de permissions

      Préset (/permissions)Ce que Codex peut faireUsage recommandé

      Annexe B — Où vivent les fichiers de contexte et de configuration

      ÉlémentEmplacementRôle
      Instructions de projetAGENTS.md à la racine du dépôt (et éventuellement dans des sous-dossiers) ; global : ~/.codex/AGENTS.mdrègles permanentes chargées avant chaque tâche ; taille limitée (32 KiB par défaut d'après la documentation)
      Skills.agents/skills/<nom>/SKILL.md (dépôt) ou $HOME/.agents/skills (personnel)méthodes réutilisables, avec name et description
      Agents personnalisés.codex/agents/<nom>.toml (projet) ou ~/.codex/agents/ (personnel)champs name, description, developer_instructions
      Hooks.codex/hooks.json (projet) ou ~/.codex/hooks.json (profil) ; scripts dans .codex/hooks/réagir à un événement (avant/après un outil, démarrage de session…) ; validation obligatoire via /hooks
      Commandes personnalisées~/.codex/prompts/<nom>.md (personnel uniquement, jamais dans le dépôt)fichier Markdown → commande /prompts:<nom> ; déprécié, préférer les skills
      Configuration~/.codex/config.toml (global) ; .codex/config.toml (projet de confiance)réglages, serveurs MCP ([mcp_servers.<nom>])

      Règle pratique : AGENTS.md = règles permanentes du projet ; skill = méthode pour une tâche, partageable et invocable implicitement ; commande personnalisée = méthode personnelle, non partagée, à invoquer explicitement (mécanisme déprécié) ; agent = rôle spécialisé ; hook = réaction automatique à un événement de Codex ; MCP = accès à un outil ou à une source externe.
