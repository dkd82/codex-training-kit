      Jour 2 — Présentation des travaux pratiques

      Thème du jour : fonctions avancées, tools et agents spécialisés. Ce guide couvre les TP 4 à 7. Les TP 1 à 3 font l'objet du guide du Jour 1.

      Le fil rouge : un mini-outil de facturation

      Vous poursuivez le même projet qu'hier : un outil de facturation en ligne de commande, en Python. Aujourd'hui vous l'enrichissez avec une action personnalisée (TP 4), un tool branché sur une API interne (TP 5), un duo d'agents qui construit une fonctionnalité (TP 6), puis vous menez un refactor assisté sur un code hérité (TP 7). C'est le « projet fil rouge » du programme.

      ★
      Votre état d'esprit pour tous les TP

      Codex accélère, vous gardez la maîtrise : plus l'outil est autonome (skills, tools, agents), plus vous devez encadrer : permissions minimales, validation humaine aux points clés, tests et relecture du diff.

      Ces durées sont indicatives ; chaque TP contient des parties « cœur » (à faire) et « bonus » (si vous avez de l'avance). Ils correspondent aux « mises en pratique du Jour 2 » du programme. Le TP 8 est un bonus : à faire si le temps le permet en fin de journée, sinon en autonomie après la formation — il n'est pas nécessaire pour la suite du parcours.

      Les 4 réflexes à appliquer à chaque TP

      1. Cadrer : un prompt structuré (objectif, contraintes, style, format attendu).
      2. Planifier avant de coder : demander un plan en lecture seule, le relire, le corriger.
      3. Contrôler : relire le diff (git diff), lancer les tests, ne jamais accepter à l'aveugle.
      4. Protéger : permissions minimales, aucun secret dans le code ni dans les prompts partagés.

      TP 4 — Créer une action personnalisée pour organiser une feature

      RubriqueDétail
      Jour / duréeJour 2 — 40 minutes (indicatif)

      Compétencestemplate d'instructions réutilisable, skill Codex, workflow en 5 étapes

      Objectifs

      • Transformer un long prompt récurrent en action personnalisée réutilisable par toute l'équipe.

      • Tester la skill sur une vraie feature et l'améliorer.

      Vous obtenez .agents/skills/nouvelle-feature/SKILL.md : une coquille pleine de TODO. Lisez aussi specs/export_csv.md (la feature de test).

      Étape 1 — Compléter la skill

      Une skill est un dossier contenant un fichier SKILL.md : un en-tête YAML avec name et description, puis les instructions. La description est essentielle : c'est elle qui permet à Codex de décider quand utiliser la skill.

      Complétez SKILL.md : la description, l'objectif, 5 étapes (cadrer, planifier, tester d'abord, implémenter, documenter), les contraintes et les livrables. Vous pouvez vous faire aider par Codex, mais relisez tout : l'objectif est que la skill traduise VOS règles.

      Champ libre : écrivez votre propre prompt par-dessus le squelette. Enregistré automatiquement sur cet appareil.

      Étape 2 — Vérifier que Codex voit la skill

      Démarrez (ou redémarrez) Codex dans le dossier du projet, puis listez les skills disponibles avec /skills. Votre skill nouvelle-feature doit apparaître.

      Étape 3 — Invoquer la skill sur une vraie feature

      Invoquez-la explicitement (par /skills, ou en tapant $nouvelle-feature), en donnant la feature à traiter : celle de specs/export_csv.md. Observez le déroulement : Codex suit-il les 5 étapes dans l'ordre ? S'arrête-t-il pour vous laisser valider le plan ?

      Squelette de promptà remplir
      Champ libre : écrivez votre propre prompt par-dessus le squelette. Enregistré automatiquement sur cet appareil.

      Étape 4 — Évaluer et améliorer la skill

      Répondez honnêtement : la skill a-t-elle été suivie ? À quelle étape Codex a-t-il dérivé (code avant les tests ? plan sauté ?) ? Modifiez une instruction pour corriger le comportement, puis relancez sur une autre petite feature de votre choix.

      Étape 5 — Comparaison (bonus)

      Refaites la même feature sans la skill (prompt libre). Comparez la régularité et la qualité des livrables. Qu'apporte le template d'instructions ?

      Livrables et critères de réussite

      Pièges à éviter

      • Description trop vague (« aide pour le code ») : Codex ne saura pas quand l'utiliser.
      • Skill trop longue : plus elle est longue, plus elle consomme de contexte. Restez concis.
      • Dupliquer AGENTS.md dans la skill : AGENTS.md = règles permanentes du projet ; skill = méthode pour une tâche.

      Pour aller plus loin

      • Créez une seconde skill (par exemple revue-de-code) et comparez avec une action « prompt dans un fichier ».
      • Partagez la skill dans le dépôt : elle vit dans .agents/skills/ et se versionne comme du code.

      TP 5 — Ajouter un tool personnalisé (API interne) à Codex

      RubriqueDétail
      Jour / duréeJour 2 — 75 minutes (indicatif) : partie A 25 min, partie B 50 min
      StarterStarters/tp5_tool
      Compétencesfunction calling, schéma d'outil, validation des entrées, serveur MCP, permissions
      Livrable2 outils en lecture seule (statut d'une facture, factures d'un client) utilisables depuis Codex

      Objectifs

      • Partie A : comprendre la boucle du function calling avec l'API (déclarer, demander, décider, exécuter dans votre code, répondre).
      • Partie B : donner ces mêmes outils à Codex via un serveur MCP, puis les utiliser en langage naturel.
      • Appliquer la sécurité : lecture seule, validation des arguments avant tout appel, aucun secret dans le code.

      Le décor

      Vous disposez d'une « API interne » factice (api_interne/serveur.py) qui expose des clients et des factures, protégée par une clé passée dans l'en-tête X-API-Key. Vous allez écrire deux fonctions (outils.py), puis les exposer : à l'API OpenAI (partie A) et à Codex (partie B).

      Mise en route

      Windows PowerShellpowershell
      cd tp5_tool
python -m venv .venv; .venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python api_interne\serveur.py          # laissez ce terminal ouvert (API interne sur le port 8765)

      Dans un second terminal (même dossier), testez l'API interne :

      Test de l'API interne (Bash)bash

      Test de l'API interne (PowerShell)powershell
      Invoke-RestMethod -Uri http://127.0.0.1:8765/factures/F-001 -Headers @{ "X-API-Key" = "demo-key" }

      Vous devez voir la facture F-001 (statut emise, total TTC 18.00). Sans l'en-tête, l'API répond 401.

      Livrables et critères de réussite

      Pièges à éviter

      • Déclarer le serveur avec python sans chemin de venv : Codex lance un autre interpréteur, mcp est introuvable.

      • Description d'outil vague : le modèle ne sait pas quand l'utiliser.
      • Faire confiance au schéma seul : toujours valider dans votre code.
      • Oublier de démarrer l'API interne (premier terminal) : l'outil répond « connexion refusée ».

      • Ajoutez l'option enabled_tools dans la configuration pour n'activer que certains outils du serveur.

      TP 6 — Orchestrer un duo d'agents (architecte + développeur), puis déléguer en parallèle

      RubriqueDétail
      Jour / duréeJour 2 — 60 minutes (indicatif)
      StarterStarters/tp6_agents (+ specs/relances.md de base_facturation)
      Compétencesagents spécialisés, rôles et périmètres, orchestration multi-agents (séquentielle et parallèle), validation humaine
      Livrabledocs/design_relances.md (architecte) puis la fonctionnalité « relances » implémentée et testée (développeur)

      Objectifs

      • Définir deux agents spécialisés avec un rôle, une description et des instructions précises.
      • Orchestrer un enchaînement architecte → validation humaine → développeur.
      • Déclencher une délégation en parallèle (plusieurs sous-agents sur un même changement) et observer comment Codex consolide leurs résultats.
      • Constater les bénéfices (design relu avant le code) et les limites (consommation, périmètre à surveiller).
      i
      Qui orchestre ?

      Ce TP illustre deux formes d'orchestration multi-agents : un enchaînement séquentiel avec porte humaine (architecte → vous → développeur, étapes 1 à 4), et une délégation en parallèle (plusieurs sous-agents sur les mêmes fichiers, étape 5). Dans les deux cas, c'est Codex lui-même — la session avec qui vous discutez — qui orchestre, dès que vous le lui demandez explicitement. Il n'existe pas d'agent « orchestrateur » à définir : les seuls agents intégrés sont default (généraliste), worker (implémentation) et explorer (exploration en lecture seule). Voir aussi la diapositive « Qui orchestre, et comment le déclencher ? ».

      La fonctionnalité à construire

      Les relances de paiement : détecter les factures émises et échues, déterminer un niveau (rappel_1, rappel_2, mise_en_demeure) selon les jours de retard, et générer le texte de la relance. Lisez specs/relances.md : règles, API attendue, commande CLI.

      Mise en route

      Repartez de votre copie de base_facturation (9 tests au vert) et copiez le dossier .codex du starter.

      macOS / Linux / Git Bashbash

cd base_facturation && python -m pytest -q

      Étape 1 — Définir les deux agents

      Ouvrez .codex/agents/architecte.toml et .codex/agents/developpeur.toml. Un agent personnalisé est un fichier TOML avec trois champs : name (identifiant), description (quand l'utiliser) et developer_instructions (comment il se comporte). Remplacez tous les TODO.

      Cahier des charges des agents :

      ArchitecteDéveloppeur
      Missionproduire docs/design_<feature>.md à partir d'une spécificationimplémenter le design, tests d'abord
      Il écrituniquement dans docs/dans facturation/ et tests/
      Il ne fait jamaisécrire du code applicatifmodifier le design, casser les tests, ajouter une dépendance

      Étape 2 — Lancer l'architecte

      Démarrez Codex dans le projet. Demandez à l'agent architecte de produire le design de la fonctionnalité, en précisant qu'il doit attendre son résultat avant toute suite. Relisez ensuite docs/design_relances.md : signatures, cas limites (frontières 14/15/29/30 jours), plan de tests.

      Squelette de prompt (à compléter)à remplir
      Champ libre : écrivez votre propre prompt par-dessus le squelette. Enregistré automatiquement sur cet appareil.

      Étape 3 — Valider le design (porte humaine)

      Vous êtes le point de contrôle. Relisez le design et vérifiez : les frontières de retard sont-elles correctes ? Le cas « client introuvable » est-il traité ? Les tests couvrent-ils tous les statuts ? Corrigez le design si nécessaire (par un message à l'architecte) avant de passer au développeur.

      Étape 4 — Lancer le développeur

      Demandez à l'agent développeur d'implémenter la fonctionnalité conformément au design validé : tests d'abord, puis code, puis python -m pytest -q au vert.

      Squelette de prompt (à compléter)à remplir
      Champ libre : écrivez votre propre prompt par-dessus le squelette. Enregistré automatiquement sur cet appareil.

      Étape 5 — Revue, orchestration en parallèle et rétrospective

      1. git status et git diff : le développeur a-t-il touché au design ? à des fichiers hors périmètre ?
      2. Lancez /review (ou codex review --uncommitted) sur l'ensemble.
      3. Orchestration en parallèle (si le temps le permet) : dans un seul prompt, demandez à Codex de relire facturation/relances.py et tests/test_relances.py avec plusieurs sous-agents en parallèle, un par angle d'analyse, puis d'attendre tous les résultats avant de résumer.
      4. Testez la commande : créez une facture échue puis python -m facturation --data donnees relances --date 2025-03-01.
      5. Rétrospective en 3 questions (voir « Pour aller plus loin »).

      Champ libre : écrivez votre propre prompt par-dessus le squelette. Enregistré automatiquement sur cet appareil.
      i
      Qui orchestre ?

      Il n'existe pas d'agent « orchestrateur » à créer pour ça : c'est la session Codex elle-même qui démarre les sous-agents demandés, attend leurs résultats si vous le précisez, puis vous renvoie une réponse consolidée. Chaque sous-agent a son propre fil, consultable dans l'application. Ce pattern consomme plus de tokens qu'un enchaînement classique : réservez-le aux relectures qui gagnent vraiment à être menées sous plusieurs angles à la fois.

      Test de la commandebash
      python -m facturation --data donnees ajouter-client --id C1 --nom ACME --email compta@acme.example
python -m facturation --data donnees creer-facture --numero F-001 --client C1 --emission 2025-01-10 --echeance 2025-02-09 --ligne "Stylo;10;1.50"
python -m facturation --data donnees relances --date 2025-03-01

      Livrables et critères de réussite

      Pièges à éviter

      • Demander « fais tout » à un seul agent : vous perdez la séparation des rôles et la porte de validation.
      • Enchaîner développeur après architecte sans relire le design.
      • Croire qu'un rôle décrit en texte est une garantie : vérifiez avec git status et git diff.
      • Multiplier les agents : chacun consomme des tokens ; commencez avec deux.

      Pour aller plus loin

      Rétrospective : (1) Qu'a évité l'architecte ? (2) Où le développeur s'est-il écarté du design, et pourquoi ? (3) Faut-il un troisième agent (relecteur) ? Écrivez son fichier TOML. (4) Quelles relectures, dans votre équipe, gagneraient à être menées par plusieurs agents en parallèle plutôt qu'une seule à la fois ?

      TP 7 — Générer un plan de refactor automatisé sur un projet existant

      RubriqueDétail
      Jour / duréeJour 2 — 45 minutes (indicatif)
      StarterStarters/tp7_refactor
      Compétencesanalyse de code hérité, plan de refactor, tests de caractérisation, petits pas, revue
      Livrableun plan de refactor critiqué et validé, puis les premières étapes appliquées avec tests verts

      Objectifs

      • Faire produire à Codex un plan de refactor en lecture seule, puis le critiquer avec une grille.
      • Refactorer en petits pas, en s'appuyant sur des tests de caractérisation qui protègent le comportement.
      • Distinguer un refactor (même comportement) d'une évolution (comportement modifié).

      Le code hérité

      legacy/devis.py calcule des devis : total, remise (VIP ou non), TVA par pays, mise en forme, historique des devis traités. Il fonctionne, mais il est difficile à lire et à maintenir (nombres magiques, fonction monolithique, état global, duplication). tests/test_caracterisation.py fige son comportement actuel, bizarreries comprises.

      Ouvrez .codex/hooks/bloquer_commandes_risquees.py : trois TODO. La règle est volontairement simple : le hook lit ce que Codex lui envoie sur l'entrée standard, cherche un motif interdit dans le texte, et retourne un code de sortie. 0 = autorisé. 2 = bloqué, avec la raison écrite sur la sortie d'erreur (stderr) — c'est la convention documentée par OpenAI pour les hooks.

      Squelette de prompt (à compléter)à remplir
      Champ libre : écrivez votre propre prompt par-dessus le squelette. Enregistré automatiquement sur cet appareil.

      Étape 3 — Déclarer le hook dans Codex et lui faire confiance

      Ouvrez Codex dans ce dossier. Comme le hook n'est pas encore connu de Codex (ou a changé), Codex doit vous demander de le réviser et de lui faire confiance avant qu'il ne s'exécute — c'est le mécanisme de confiance basé sur l'empreinte (le hash) du hook.

      Séquence dans Codextext

      Complétez prompts_perso/nouvelle-fonctionnalite.md : la description, l'indice sur les arguments, et le corps du prompt (réutilisez la structure objectif / contraintes / style / format attendu). Copiez-le ensuite dans votre dossier personnel, puis invoquez-le.

      !
      Un mécanisme déprécié

      La documentation officielle marque les custom prompts comme dépréciés, au profit des skills (TP 4) : une skill peut être partagée via votre dépôt et invoquée implicitement par Codex, ce qu'une commande personnalisée ne permet pas — elle reste personnelle, et toujours explicite (/prompts:nom).

      Livrables et critères de réussite

      Pièges à éviter

      • Un motif trop large (bloquer tout /) qui empêche des commandes légitimes : testez toujours les cas qui doivent passer, pas seulement ceux qui doivent bloquer.
      • Oublier git init : la commande du hook dans hooks.json a besoin d'un dépôt Git pour localiser le script.
      • Renvoyer des informations sensibles dans la sortie du hook (elle peut être conservée sur disque) : ne jamais y écrire de secret.
      • Confondre commande personnalisée et skill : la commande personnalisée est personnelle et explicite ; la skill est partageable et peut être invoquée implicitement.

      Pour aller plus loin

      • Ajoutez un second hook PostToolUse qui journalise les commandes exécutées.
      • Explorez les autres types de hooks (SessionStart, UserPromptSubmit…) dans la documentation officielle.

      Règle pratique : AGENTS.md = règles permanentes du projet ; skill = méthode pour une tâche, partageable et invocable implicitement ; commande personnalisée = méthode personnelle, non partagée, à invoquer explicitement (mécanisme déprécié) ; agent = rôle spécialisé ; hook = réaction automatique à un événement de Codex ; MCP = accès à un outil ou à une source externe.

      Qui orchestre plusieurs agents ? D'après la documentation officielle, il n'existe pas d'agent « orchestrateur » prédéfini : les agents intégrés sont default (généraliste), worker (implémentation) et explorer (exploration en lecture seule). C'est la session Codex elle-même qui orchestre, sur demande explicite (« lance plusieurs agents en parallèle », « un agent par sujet ») ou sur instruction d'AGENTS.md/d'une skill : elle démarre les sous-agents, attend leurs résultats si demandé, puis consolide une réponse. Chaque sous-agent a son propre fil, consultable dans l'application.
