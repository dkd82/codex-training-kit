Comment utiliser ces ateliers

  • Le Jour 1 portait sur votre propre efficacité. Le Jour 2 porte sur industrialiser : les agents sur des tâches complexes, les conventions d'équipe, l'automatisation, et une stack commune.
  • Vous partez d'un état de référence propre (pulselab_jour2_starter.zip), donc un atelier du Jour 1 non terminé n'a pas d'importance.
  • Mêmes conventions qu'au Jour 1 : des modes plutôt que des produits (voir le tableau), des encadrés en pointillés pour les prompts que vous écrivez vous-même, des coches enregistrées dans votre navigateur, un journal IA en bas de page.
  • Une branche par atelier, à partir de main. main reste propre.
Règles de sécurité inchangées : aucun secret, aucune donnée confidentielle, aucun résultat non publié dans les prompts. Les agents reçoivent le minimum permissions ; gardez les approbations activées pour les commandes shell ; lisez chaque diff.

Les cinq modes (même vocabulaire qu'au Jour 1)

  • Votre tableau du Jour 1 s'applique toujours. Aujourd'hui vous utilisez AGENT bien plus : dans Kilo Code, les permissions se règlent dans kilo.jsonc (clé permission : allow, ask ou deny, par outil).

TP 2.1 · Refactoring à grande échelle avec un agent

Objectifs pédagogiques
  • Lancez un refactoring multi-fichiers avec plan, incréments, garde-fous et vérification.
  • Détectez un agent qui affaiblit les tests ou dérive hors périmètre.

Conception cible. (1) une dataclass immuable Config remplace le global CONFIG dict ; (2) un Run la dataclass remplace le dict run ; (3) pathlib.Path remplace os.path et glob ; (4) logging remplace print pour les messages (le tableau de résultats affiché par print_table reste un print); (5) des annotations de type sur les fonctions publiques.

Invariants. Le CSV de résumé et les pulses détectées ne changent pas (tests/golden/* doit être intact); l'interface en ligne de commande ne change pas ; aucune nouvelle dépendance.

2.2.4Tests basés sur les propriétésEDITAGENT8 min
  • Écrivez les trois propriétés ci-dessous sous forme de tests. Avec hypothesis (si vous pouvez l'installer) : @given(...) avec un nombre borné d'exemples. Sans cela : une boucle sur 50 graines avec numpy.random.default_rng(seed).
les trois propriétés
# Propriété 1 : remove_offset
#   pour tout tableau de flottants x (longueur >= 2) : l'entrée n'est pas modifiée, la moyenne du résultat est ~0,
#   et l'appliquer deux fois donne le même résultat.
# Propriété 2 : dominant_frequency
#   pour toute fréquence entière f dans [2, 200] Hz, fs = 1000 Hz, un sinus de n'importe quelle amplitude sur n'importe quel offset
#   donne dominant_frequency(x, fs) == f à 0.3 Hz près.
# Propriété 3 : find_pulses
#   pour tout tableau : les indices sont croissants, des indices consécutifs diffèrent d'au moins le gap,
#   chaque échantillon renvoyé est au-dessus du seuil, et aucun indice n'est le premier ou le dernier échantillon.
  • Demandez à l'assistant une première version, puis lisez les assertions et les plages d'entrée : une propriété trop faible (ou une plage qui évite les cas intéressants) ne prouve rien.

TP 2.3 · Mini-atelier d'orchestration multi-agents

Objectifs pédagogiques
  • Découpez une tâche en briefs indépendants et cadrés, exécutez-les dans sessions isolées et intégrer les résultats.
  • Décidez, avec des preuves, si le multi-agent en valait la peine ici.

Vous êtes le orchestrateur. Trois sous-agents (trois sessions distinctes, ou les sous-agents de votre outil s'il en propose) travaillent sur fichiers disjoints. Vous intégrez ensuite. Si votre outil ne peut pas exécuter des sessions en parallèle, exécutez-les l'un après l'autre, chacun dans une session neuve : c'est l'isolation qui compte, pas la simultanéité.
